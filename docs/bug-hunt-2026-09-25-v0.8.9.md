## 缺陷 1【已修并部署】mission tick 停止后状态机永久 busy（loading 卡死无熔断）

### 事实层：代码（读源码确认）

`src/ScenarioRunner.cs` 的 `ScenarioProbe.OnMissionTick`：

1. `State == loading` 分支算完双方存活数后直接 `return`（原 1259–1275）；
2. abort 的 `_endRequested` 判定（原 1307）与 `DurationCapSeconds` 超时判定（原 1327–1332）
   都在 `if (State != RunStateRunning) return;`（原 1277）**之后**
   ⇒ loading 期间既不计入时长上限，也不消费 abort 请求；
3. `LastHeartbeatUnix` 全仓库只有两处**写入**（start 时、running 每 tick），
   **没有任何读取点** ⇒ 心跳是「写了没人用」的死字段，不存在看门狗。

### 后果层：实测（同一时刻的内部对照）

2026-09-25 11:40:31 用不存在的场景名 `bridge` 触发原生崩溃后，
11:50:40–11:50:48 连续 5 份 status 响应（`commands/done/*.json`）均为：

```
state=loading  busy=true  elapsedSec=608~617（已超 durationCapSec=600）
readiness.verdict=stalled  ticks=0  missionTime=0  result=null
```

同一时刻的两侧对照决定了修复该挂在哪里：

| 回调 | 11:50 时的表现 | 结论 |
|---|---|---|
| `SubModule.OnApplicationTick`（主线程） | 仍在跑 —— CommandPump 写出了 5 份 done 响应（mtime 11:50:40–48） | **可用** |
| `Mission.OnMissionTick` | 已停 —— EngineProbe 报 `ticks=0`、`missionTime=0` | 不可用 |

⇒ 熔断挂 mission tick 等于挂在「已经停掉的那条路径」上，必须挂主线程。

项目自己在 `ScenarioRunner.cs` 注释里也记录过同一现象（"mission 卡 loading/busy，abort 无效"），
但只作为兵种扫描流程的规避说明，**根因未修**。

### 影响

一次 loading 卡死 ⇒ `Busy` 永久为 true ⇒ 后续 `start_battle` 全部被拒
（"已有一场推演在进行中"）⇒ 只能重启游戏才能恢复。

### 修复（本次落地）

- `src/ScenarioRunner.cs`：新增 `Watchdog()` 与 `WatchdogLoadingSeconds = 120f`
  - 判据：自 `LastHeartbeatUnix` 起超过阈值仍无任何 mission tick ⇒ 判定卡死；
  - 阈值：loading 用 120 s（正常 agent 生成只需数秒，留足余量）；
    running 用 `DurationCapSeconds + 60`，保证不会抢在 durationCap 正常收尾之前误杀；
  - 收尾顺序：**先**落状态（`State=error`，result 带 `stuckState`/`stuckSec`，`Busy` 立即转 false），
    **后**尝试 `Mission.EndMission()`（引擎已异常时大概率无效 —— 历史实测 abort 无效，但不新增崩溃）。
- `src/SubModule.cs`：`OnApplicationTick` 在 `CommandPump.Pump()` 之后调用 `ScenarioRunner.Watchdog()`。
