# 配置文件工具安全：为什么"读配置"不能用 mod 自己的 load 函数（2026-10-08）

> **一句话**：**`RBMConfig.parseXmlConfig()` 不是只读函数** —— 它的末尾**无条件**落盘，
> 而且**永远写真实配置路径**，**忽略你 Load 的是哪个文件**。
> ⇒ 任何"拿副本做只读往返验证"的做法都会**静默覆写玩家的真实配置**。
>
> **本文登记这个已知风险**，并给出 BlBridge 侧已落实的规避（A4，见 §三）。
>
> ★ **2026-10-08 扩展**：本文现在记录**三起独立事故**（都属于"写路径的报告与事实不符"），
> 以及**每条各自的回归断言**。见 §四、§五、§六。

## 三、规避（BlBridge 侧已落实 + 给 MOD 侧的纪律）

### 3.1 已落实（A4，`tools/bl_mcp.py`）

1. ★ **`bl_read_config` 真只读**：走 `_read_text()` + `_scan()`（纯文本/正则解析），
   **从不实例化任何 mod 的 Config 类**、**从不调用任何 mod 的 parse/load 函数**；
2. 自测里有一条**反向对照**：**读前/读后文件 sha256 必须相同** ——
   若将来有人把实现改成调 mod 的函数，这条会**立刻变红**；
3. `bl_apply_config` 写前**备份**、写后**回读校验**，并在返回里**回显实际写入的绝对路径**
   （`path` + `pathSource`）+ `restartRequired` / `restartNote`。

### 3.2 给任何"配置工具"的纪律（写代码前先看）

| 规则 | 理由 |
|---|---|
| **"读"不得调用 mod 自己的 `Load`/`parse` 函数** | 它可能带副作用（本例：无条件落盘）|
| 只读实现用**纯文本/XML 解析**（`io.open` + 正则 / `xml.etree`） | 与 mod 语义解耦，不可能写盘 |
| ★ **必须回显"实际操作的绝对路径"** | 本项目"文件目标不可信"有两面：**既会操作错的文件**（B1：改了没有消费者的 Warbandlord 残留档），**也会以为操作的是另一个文件**（本事故）|
| **写后回读校验**，且回读走**同一套解析口径** | 防"写进去了但格式/位置不对 ⇒ mod 读不到" |
| 改动源文件前**先备份**，并让备份路径可见 | 出事能还原（本事故能还原全靠 sha 逐字节比对）|
| 目标不存在时**明确报错，不回退默认** | 静默回退会造成"指定了 A 却动了 B" |

### 3.3 ★ 另一面：RBM 的 `config.xml` 有**两种格式并存**

实测 `Configs\RBM\config.xml`（683 项）：

| 形式 | 写法 | 谁在读 | 路径口径 |
|---|---|---|---|
| **②** | `<Option id="X" value="V" />` | Warbandlord 遗产 | `Category/Group/SubGroup` 的 **id** 拼接（468 项）|
| **①** | `<Tag>V</Tag>` | **RBM 自己的 loader** | **祖先标签名**拼接，如 `RBMCampaign/BadDataCleanupEnabled`（215 项）|

★ **写回必须保持原格式** —— 把形式①改写成 `<Option .../>` ⇒ **RBM 读不到** ⇒ 又是"改了没生效"。
（`bl_apply_config` 已按形式分别写回，并有自测断言"形式①不会被改写成 Option"。）

★ 形式①的路径**必须带祖先**：`Enabled` 在 `RBMTournament` / `RBMAI` / `RBMCombat` / `RBMCampaign`
**四处重复** ⇒ 只用标签名会**四路撞车**。

## 四、事故 2：`bl_apply_config` 成功分支返回**裸 dict**（写完再抛）

### 症状（Lead 实测，第一次调用就炸）
```
call_tool('bl_apply_config', {"edits":[...], "path":"<RBM config>"})
→ ValueError: too many values to unpack (expected 2)
```
**读工具正常**；**写工具经派发必炸**（dry_run 与真写都炸）。**直调正常** —— 所以自测里发现不了。

### 根因
```
派发点  : ok, payload = apply_config(..., _structured=True)   ← 期望【元组】
返回点  : return result                                        ← 成功分支返回【dict】
          _structured=True 的契约是 (ok, payload)，但成功分支是裸 dict ⇒
          解包 dict 得到的是**它的键**（4/10 个）⇒ too many values to unpack
```

### ★ 为什么延后暴露、又为什么由 A4 激活
- **HEAD 里这个洞就存在**（成功分支一直返回裸 dict）；
- 但**长期不可达**：没有 `path` 参数时永远先过 B1 闸门，
  而目标模块（Warbandlord）**已卸载** ⇒ 总走 `(False, st)` 错误分支 ⇒ **成功分支没人走**；
- **A4 加了 `path=`（跳过闸门）⇒ 成功分支第一次可达 ⇒ 潜伏洞被激活**。

### ★★ 为什么这条"严重"（不是普通崩溃）
真写顺序：**备份 → 写文件 → `os.replace` → 回读校验 → `return`**。
异常发生在**返回之后**（调用方解包时）⇒ **文件已经改完并落盘，但调用方只看到 `ValueError`**
⇒ 任何调用方都会以为"改失败了"，而**实际上配置已经被改**。
★ 这正是本项目最防的"**报告与事实相反**"，而且发生在**写路径**上。

### 修法（已落实）
1. `apply_config` 的**所有**分支统一走局部 `_ret(payload, ok)` ⇒
   `_structured=True` **恒返回 `(ok, payload)` 元组**；
2. 把该约定**写死在 docstring** 里（防再犯）；
3. 派发点加**形状断言**：契约若再被破坏，立刻给**可读错误**
   （`internal_return_contract_violation`）+ 提示"文件可能已被改，请回读确认"，
   而不是让人看 `too many values to unpack`；
4. **回归断言**（`bl_selftest.py`，★ **全部经 `call_tool()` 派发**）：
   dry_run 不抛 / 真写不抛 / `verified` 回读 = 期望值 / 错误路径结构化不抛。

### ★ 教训（Lead 定，已写进 docstring）
> **"直调通过"不等于"派发路径通过"。** 写路径的测试**必须走真实调用入口**。
> 我原来的 11 条 A4 断言**全是直调** —— 所以漏掉了它。这是个**方法级**漏洞，不是遗漏一条用例。

## 五、事故 3：`bl_apply_rts_config` 不转发 `path`（**我的自测写到了真档**）

### 事故经过（诚实记录）
我为"行尾不变量"写自测时，**本意**是写一个**临时副本**：
```python
bl_mcp.call_tool("bl_apply_rts_config",
                 {"edits":[...], "path": <临时副本>})     # ← 看起来完全正确
```
**实际**写到了玩家的**真实** `RTSCameraConfig.xml`：
```
改动: <ElevatedHeight>10</ElevatedHeight> → 9
时间: 2026-10-08 03:40:18（我跑 bl_selftest 那一次）
```

### 根因（第三类"文件目标不可信"）
```
bl_apply_rts_config 的派发：既不【声明】`path`、也不【转发】`path`
   → bl_rts.apply(edits, dry_run=..., allow_missing=...)     ← path 从未传入
   → bl_rts.apply 里 `path = path or config_path()`          ← 落到【真实】配置
```
★ 危险点：参数"看起来传了"、返回值**完全正常**、**零报错** —— 教科书级**静默失效**。

### 处理
1. **立即按事故前的备份逐字节还原**（并用一个**事故前早已存在**的独立备份交叉验证：
   `RTSCameraConfig.xml.bak_20260926_193053` ⇒ 与之逐行相同）；
   sha 复核：`346C4494CF1FE451…` = 备份 sha，3343 B，CRLF 原样，`ElevatedHeight=10`；
2. 两个 RTS 工具**声明并转发 `path`**，返回回显**绝对路径 + `pathSource`**；
3. 见 §六的**通用断言**。

### ★★ 教训（已立为项目纪律）
> **凡"新增参数"必配"参数被转发"的断言** —— 不能只测"函数接受这个参数"，
> 要测"这个参数**真的改变了目标**"。
> **取证法（双向）**：传一个**非默认目标**，然后断言
> ① 非默认目标**变了**；② **默认目标 sha 不变**。

## 六、通用断言 `assert_param_retargets()`（可复用）

落地位于 `tools/bl_selftest.py`，签名：

```python
assert_param_retargets(tool, args_fn, default_path, copy_path, label)
```

判据（**双向**）：

| 断言 | 防什么 |
|---|---|
| ① 副本 **被改变** | 参数被丢弃（根本没生效）|
| ② **默认目标 sha 不变** | 参数被丢弃后落到默认真档（**本次事故**）|
| ③ 返回里回显的 `path` == 副本绝对路径 | 报告与事实不符 |

⚠️ **只断言 ① 不够** —— 若某个中间层"顺手"改了默认目标，① 仍可能通过。
只有 ①+② 才锁定"**目标真的被换掉了**"。

已覆盖：`bl_apply_rts_config` / `bl_apply_config`（各自还有一条**独立的安全底线**断言：
真实配置在整个自测期间**逐字节未变**）。
**后续任何新参数请直接复用它** —— 这条若早存在，事故 3 **第一秒就会红**。

## 八、★ 报告的两个通道必须分开：`coverage`（正常）vs `skipped`（异常）

**又一起"报告与事实不符"，但方向相反**（2026-10-08，A 线自查自己的 A3 实现）：

A3 要求"物品扫描扩到全队伍 + 聚落后，**扩了范围必须在报告上可见**"。
第一版我把覆盖口径写进了 **`skipped`**：
```
skipped.Add("itemScope: 共扫 N 个 roster —— party:...; settlement:...; stash:...")
```
★ **这是错的**：`skipped` 在本项目里是**唯一**用来表达"**某一类没扫成**"的信号，
工具描述与返回都反复强调："**`skipped` 非空表示某类没扫成 —— 别把「0 条」读成「很干净」**"。
把**正常**的覆盖信息混进去 ⇒ **每次成功扫描都假报"有东西没扫成"**。

| 通道 | 语义 | 例 |
|---|---|---|
| **`coverage`** | ★ **正常**：这次扫了**什么范围** | `item: 共扫 1918 个 roster —— party:[玩家](…); party:…; settlement:…; stash:…` |
| **`skipped`** | ★ **异常**：某类**没扫成**（成员缺失等）| `Clans=null` |

### 为什么把"正常"混进"异常"通道**特别糟**（Lead 的定性：信号污染）

- 前面几起是"**异常被报成正常**"（静默失效）—— 让人**少做事**；
- 这一起是"**正常被报成异常**"（假警报）—— 让人**习惯性地忽略那个信号**。
  ⇒ 等**真有异常**时也没人看了（**狼来了**）。**两者都摧毁信号的可信度**，后者更阴。

### 判据（已落地）
- `BadDataSpec.BuildSummaryJson` 增**可选**参数 `coverage` ⇒ **独立字段**；
- ★ **未传 `coverage` ⇒ 不出现该键**（不凭空造字段）；
- ★ **反向对照**：覆盖口径**只**出现在 `coverage`，不以 `skipped` 名义出现；
- 工具描述写明"**两者别混读**"，并点出操作含义：
  **看 `coverage` 才能判断「物品 0 条」到底是扫遍了还是只扫了一处。**

## 九、附：一个有用法价值的工具技巧（Lead 实测推荐）

查"某文件里某模式的**全部**出现点"时，用 `search_source` 的 **`filePattern`** 限定文件，
一次命中、不用人工过滤：
```
search_source(query="\\(PartyBase\\)",
              filePattern="*SandboxAgentStatCalculateModel.cs")
→ 6 处命中，行号一次到齐（R2 评估就是靠它定位"崩点不止一处"）
```
★ 比"全库搜再筛"省得多 —— 尤其当同名模式在 220 个文件里出现 828 次时。
