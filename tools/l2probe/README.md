# `tools/l2probe` —— L2 API 漂移探针

**一句话**：把上游 [BUTR/Bannerlord.GABS](https://github.com/BUTR/Bannerlord.GABS)（MIT）的**真实调用点**搬到本机
`TaleWorlds.*` 引用程序集上**编译**，用编译器判定"这个 API 在 1.4.8 上还能不能用"。

```powershell
python tools\l2probe\run_probe.py
# 退出码 0 = 与预期一致（含负向对照 P13 必须红）／1 = 有 CASE 与预期不符／2 = 装置问题
```

结论与短名单见 **`docs/l2-api-drift-1.4.8.md`**。

---

## 为什么需要它

上游声明支持的游戏版本是 `v1.3.15` / `v1.3.13` / `v1.2.12`，本机是 **v1.4.8** —— 它的代码**从没在 1.4.8 上验证过**。
在抄任何东西之前，必须先知道"哪些抄得动、哪些抄不动"，而且要**可复现**（游戏升级后能再跑一遍）。

## 判据

| 判据 | 工具 | 能测到 |
|---|---|---|
| **第一层：编译** | Roslyn `csc`（与 `build.ps1` 同款编译器与引用集） | API 存在性 + 签名兼容 |
| **第二层：成员名核对** | `ilspycmd` 反编译目标类型，比对成员名 | 字符串反射（`AccessTools2.…(typeof(X), "字段名")`）—— 编译期测不到的那一类 |
| **第三层：行为** | 真机 | **两层都测不到**：只能跑起来验。每个工具落地时仍须真机判据 |

## 文件

| 文件 | 是什么 |
|---|---|
| `L2ApiProbe.cs` | 探针本体。每个 `// ───────── CASE Pxx` 是一段**上游的真实调用点**，注释里标了上游 `文件:行` 出处 |
| `run_probe.py` | 执行器：收集引用程序集 → 编译 → 把编译器错误**按 CASE 归纳** → 与预期表比对 |
| `README.md` | 本文件 |

## 三条纪律（都是踩出来的）

1. **必须有负向对照**。`EXPECT_FAIL = {"P13"}`：P13 是上游 v1.3.13 **之前**的写法，在 1.4.8 上本就不该存在
   （实测 `CS1061 MobilePartyAi 未包含 SetMoveGoToPoint`）。它**必须红** ——
   一个恒绿的探针测不出任何东西，它红了才说明"编译器真的在判定"。
   哪天它变绿了，说明探针失效了或游戏把老 API 加回来了，两种情况都该有人看一眼。
2. **装置错误不许冒充通过**。首版把原生 DLL（`TaleWorlds.Native.dll`）当引用传给 csc，
   csc 报 `CS0009` 后**中止编译**、源码错误一个都没报，而统计只挑"归到 CASE 的错误" ⇒
   打印「通过 22/22、退出码 0」。现在：引用前判 PE 的 CLI 数据目录（非托管直接跳过），
   且**任何没归到 CASE 的 `error CS` 算装置错误**（打印 + 退出码 2）。
3. **FAIL 要回读原文再定性**。首版 P02/P22 的 FAIL 全是**探针自己写错**（`float` 写成 `int`、漏了一个 `using`），
   照抄那一版结果就会凭空造出两个"漂移"。

## 加新 CASE 的规矩

- 只抄**上游的真实行**，并在注释里给出出处（`上游文件:行`）—— 不要凭印象写"大概是这样"。
- 只有**一段** API 的 CASE 才容易定位；一个 CASE 里塞多个调用，第一个报错会掩盖后面的。
- 新 CASE 默认"应当编译过"；要声明成"应当编译不过"，把它加进 `run_probe.py` 的 `EXPECT_FAIL` 并**写明理由**。
- 加完之后**先看退出码**：`0` 才是"与预期一致"。不要只看那行"通过 N/M"。
